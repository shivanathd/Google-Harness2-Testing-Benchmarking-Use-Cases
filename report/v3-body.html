Harness² on the Bench

Google's Harness² rewrites an agent's prompts, skills and scripts while the model stays fixed. We ran it on our own benchmark and on Google's own legal tasks, with a weak local model and with Claude Code. We also ran the ablations the paper's claims rest on, and we audited every harness it wrote for leaked answers.

    Learnings

    What we would tell the next team

    What it wrote

    The same skill, before and after the leak guard

    Both harnesses were adopted for the ops-easy log task. Without the guard, the improver ran its own script on the task files and recorded the answers. With the guard, the proposal was rejected, retried, and came back as method only.

    Method

    How we tested

    Benchmarks

    HPB: our own 9 tasks (data, ops, SWE-style repos × easy, medium, hard) with hidden programmatic graders and fresh-seed copies. LAB: four of Google's own arbitration tasks from harvey-labs (37–59 rubric checks each), scored by a Claude rubric judge that mirrors LAB's scorer.

    Agents and improvers

    Claude Code (claude -p, Haiku 5.5) and a Google ADK agent on local qwen3:8b. Improvers: Sonnet 5.5, or Haiku 5.5 improving itself. Harness² core ran unmodified behind our adapter. Production cloud projects were never used.

    Measurement

    Pre-registered endpoints with seven dated amendments. Fresh re-rolls of every adopted harness (R=3–4). Hierarchical bootstrap with exact sign-flip tests. Fresh-seed and held-out tasks as the leak-free headline, with in-task results labelled as test-time adaptation.

    Leak and isolation defences, in layers

    1. Every model process runs in a macOS sandbox-exec profile with an environment allow-list. Reads of graders, other runs, credentials and .git are denied, writes are allowed only in the workspace, and web tools are off.
    2. Guard v1 at adoption rejects the task's own answers, its ids, and "workspace fact" blocks. Harness² retries the proposal once, then falls back.
    3. Guard v2 (hpb/leakguard.py) also rejects distinctive numbers and ids from the data, case-specific names, and 8-word passages copied from the sources.
    4. A read-only audit of every adopted harness in every arm, plus a scan of every agent and improver log for grader paths.
    5. The headline metric is data the improver never saw.

    With a trustworthy check, autoresearch's loop is simpler and cheaper. Without one, Harness² still makes progress, and its evidence-reading kept it from touching a Claude Code harness that already worked.

    Use it when

    A cheaper or local model does repeated work and fails for process reasons: running out of steps, skipping a check, forgetting to write the file. That is where we saw the gains (+0.42 on Claude Code capped at four turns, +0.97 on a local 8B model).

    Pair it with

    A stronger improver than the agent (self-improvement gave half the gain and caused a regression), the leak guard, and a held-out re-roll before you commit any CLAUDE.md or skill change.

    Skip it when

    The agent is already at ceiling (full-strength Claude Code: no change), or you expect one harness to cover a whole area: harnesses tuned on easy tasks did not transfer to harder ones.

    A recipe

    1. Collect 10 to 30 representative tasks, each with a cheap check so you can evaluate. Harness² never sees the check.
    2. Re-roll the current setup three or more times per task. Drop tasks that are always perfect or always zero.
    3. Run Harness² k=1, sandboxed, with no secrets in the agent's environment and the leak guard on.
    4. Re-roll each adopted harness on fresh instances of the same task, and compare with base outside the noise.
    5. Grep the diff for numbers, ids and names from the task inputs. Keep process; delete facts.
    6. Commit to CLAUDE.md and .claude/skills/, and keep the re-roll suite as a regression gate.
